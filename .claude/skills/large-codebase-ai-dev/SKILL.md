# Large Codebase AI Dev — 大代码量AI辅助开发质量保障

## 触发条件

满足以下任意条件时激活：
- 代码库超过10万行，或模块数超过5个
- 需要长期迭代维护的项目（非一次性Demo）
- AI辅助开发中频繁出现幻觉或跨模块乱改
- 用户提到：大项目开发、持续开发、重构、文档配套、索引、AI幻觉

## 核心工作流（5步循环）

每次开发操作必须按以下顺序执行，不可跳步。

### Step 1: 需求书面化

将口语化、情绪化、带语气词的需求描述转化为正式开发文档。

**消除中文歧义的规则：**
- 去除语气词（吧、呢、啊、嘛）
- 去除口语化表达（搞一下、弄一下、整一下）
- 将模糊量词转为精确描述（"一些"→具体数量，"差不多"→明确标准）
- 将情绪化表达转为客观描述（"这个太慢了"→"响应时间超过X秒"）

**输出格式：**
```
【功能目标】一句话描述要实现什么
【影响模块】列出涉及的模块名称
【预期行为】描述完成后的系统行为
【不涉及】明确边界，列出不改动部分
```

### Step 2: 查询agents索引

执行任何编码操作前，必须先读取项目根目录的 `agents.md` 索引文件。

**操作步骤：**
1. 读取 `agents.md`（或项目中 equivalent 的索引文件，如 `AGENTS.md`）
2. 根据需求关键词，锁定相关的历史文档路径
3. 按路径精准读取相关文档，了解历史操作记录
4. 避免全量扫描所有文件导致 Token 爆炸

**如果索引文件不存在：**
- 提示用户先初始化索引
- 参考本skill目录下的 [agents-index-template.md](agents-index-template.md) 创建索引文件

### Step 3: 生成开发计划

基于索引查询结果，输出开发计划并提交用户校验。

**开发计划必须包含：**
- 模块指向：明确改哪个模块、哪个文件
- 目录命名规范：新建文件遵循项目已有命名约定
- 影响范围分析：列出所有受影响的文件和模块
- 不改动清单：明确哪些部分不触碰

**此步骤必须暂停，等待用户确认后才继续。**

### Step 4: 执行开发 + 同步生成文档

编码完成后同步生成开发文档，不可事后补。

**文档类型：**
- 功能开发文档：新功能的设计、实现、验证记录
- Bug修复文档：问题现象、根因分析、修复方案、验证结果
- 需求落地文档：需求来源、实现方案、影响范围、验收标准

**文档存入位置：** 项目 `docs/` 目录（或项目约定的文档目录）

**文档模板：** 参考 [doc-templates.md](doc-templates.md)

**编码完成后必须：**
1. 生成对应的开发文档
2. 更新 `agents.md` 索引，添加新文档条目

### Step 5: 人工关键节点校验

无需逐行审核代码，重点校验架构层面。

**计划阶段校验：**
- 模块指向是否正确（有没有改错模块）
- 目录命名是否规范（有没有随意命名）
- 影响范围是否遗漏（有没有低估改动范围）

**开发完成后校验：**
- 留存的文档可作为回溯排查依据
- 可将文档重新投喂给AI进行二次自检
- 重点检查是否跨模块入侵

## 架构约束原则

以下原则作为"负面提示词"在开发过程中反复向AI强调。

**5条核心约束（详见 [architecture-principles.md](architecture-principles.md)）：**

1. **禁止兜底** — 不写兼容旧逻辑的fallback，旧逻辑该删就删
2. **禁止兼容** — 不为旧接口保留兼容层，接口变更直接改调用方
3. **高内聚低耦合** — 模块边界清晰，模块内功能内聚，模块间依赖最小
4. **不入侵业务** — 不跨模块改他人代码，需要改动时通过接口协作
5. **单一职责** — 一个文件/函数只做一件事，禁止混入无关逻辑

**负面提示词模板（粘贴到AI对话中）：**
```
架构约束（必须遵守）：
- 禁止兜底：不要写兼容旧逻辑的fallback
- 禁止兼容：不要为旧接口保留兼容层
- 高内聚低耦合：模块边界清晰
- 不入侵业务：不跨模块改其他模块代码
- 单一职责：一个函数只做一件事
```

## Token优化策略

1. **人工提前熟悉目录结构** — 开发者应了解项目整体结构，能精准指出文件路径
2. **精准指定路径** — 给AI指定具体文件路径，避免"全量扫描找问题"
3. **利用索引而非全量读取** — 通过 agents.md 索引锁定目标，再精准读取
4. **避免模糊需求** — 模糊需求导致多轮无效对话，消耗大量Token
5. **文档复用** — 历史文档可直接投喂给AI，避免重新分析代码

**成本对比：**
- 模糊需求模式：AI全量扫描 → 多轮试错 → Token消耗高，准确率低
- 精准路径模式：人工指定路径 → AI精准操作 → Token消耗低，准确率高

## 重构优先策略

1. 将 **1/3 ~ 1/2** 的开发时间投入重构环节
2. 重构时同步更新文档和 agents.md 索引
3. 重构后验证架构清晰度：模块边界是否依然清晰、依赖是否依然最小
4. AI辅助下重构效率大幅提升，应充分利用

## 检查清单

### 开发前检查清单

```
- [ ] 需求已书面化，无歧义表达
- [ ] 已查询 agents.md 索引
- [ ] 已锁定相关历史文档并读取
- [ ] 开发计划已生成（含模块指向、目录命名、影响范围）
- [ ] 用户已确认开发计划
```

### 开发后检查清单

```
- [ ] 开发文档已生成（功能开发/Bug修复/需求落地）
- [ ] agents.md 索引已更新
- [ ] 改动未跨模块入侵
- [ ] 未引入兜底/兼容层
- [ ] 架构边界依然清晰
- [ ] Token消耗在合理范围
```

## 关键认知

- AI是软件工程的效率工具，不是替代者
- 架构设计、流程管控、方向决策的核心环节完全无法脱离人工
- AI承担重复编码、快速重构这类"牛马型"工作
- 脱离人工管控的"完全自主开发"项目几乎没有长期可维护性
- 仅靠"一句话生成"的项目大多只能完成Demo演示，底层逻辑空洞
