## 一、功能目标

让「📤 导出」「💾 保存备份到设备」与「备份恢复」在**真实数据规模（约 50MB base64）**下，
**写入侧与读取侧都不再闪退**。

**同时守住三条底线**：
1. **不改数据模型**（题图仍保持 base64 内联）
2. **不做任何存量数据迁移**（不冒"改写 92 题图片字段"的不可逆风险）
3. **不减少任何现有能力**

---

## 二、问题现状（全部已实测量化）

### 2.1 数据规模（王先生设备真实量级）

| 来源 | 体积 |
|---|---|
| 题图 + 答案图（`questions`） | 16.4 MB |
| 笔记图片（`question_notes`） | 33.6 MB |
| **合计（备份 JSON 必须承载）** | **≈ 50 MB** |

### 2.2 写入侧

- **原链路**（`btoa(unescape(encodeURIComponent()))`）：峰值 **heapUsed 244MB / rss 489MB** → 闪退
  （实测 `tmp/measure-export-memory.mjs`）
- **方案 A 后**（`encoding:'utf8'` 直写）：去掉 3 份副本 → 合成基准实测降到 66MB
- **但真机仍闪退**（2026-09-14 实测，且"先卡几秒再退"）
- **修正一处低估**：合成基准用的是 `'A'.repeat()`（V8 按 1 字节/字符存）；从 IndexedDB 取出的 base64
  可能按 **2 字节/字符**存 → 对象图规模翻倍，真实峰值远超 66MB

### 2.3 读取侧（**本节是方案 B 被撤回的原因**）

`loadBackupFromDevice` 走 `readFile({encoding:'utf8'})` → 返回**整份 50MB 字符串** → `JSON.parse`。
实测（`tmp/measure-restore-memory.mjs`）：

| 步骤 | heapUsed |
|---|---|
| 只有 `jsonStr`（`readFile` 的返回值） | 61 MB |
| **+ `JSON.parse`（恢复峰值）** | **167 MB** |
| 逐条 `setItem` 完毕 | 177 MB |

**恢复峰值 167MB 与写入侧原来的 244MB 同量级 → 恢复照样闪退。**

> **结论**：只修写入侧 ⇒ 导出不再闪退，但导出的文件**恢复不了** ⇒ 等于没有备份。
> 这是典型的"看起来在工作其实没有"，与本轮拆掉的 FF-1 / D8 / legacy 死副本同一类。
> 故撤回"方案 B（1–2 小时）"的推荐。

### 2.4 一条时间特征（用于锁定根因方向）

用户在真机上的现象是**"先卡几秒再退"**。桥层拒绝通常**快速失败**；"卡几秒"说明它确实在
读 IndexedDB、反序列化、`JSON.stringify`——**内存被耗尽**的可能性远大于桥的限制。
本方案对两侧都做改造，因此**不依赖先把根因彻底分辨清楚**（对桥的余量也一并降低）。

## 三、方案设计：分片文件（sharded backup）

### 3.1 核心思路

把"一次性在内存里组装 50MB JSON"改为**逐片读、逐片写**：

- **写**：按 store 逐条累积，缓冲到 **≤ 2MB** 就落一片文件 → 峰值 ≈ 单条记录 + 2MB 缓冲
- **读**：读 manifest → 逐片 `readFile` → `JSON.parse` → 逐条 `setItem` → **释放该片** → 下一片
  → 峰值 ≈ 单片 2MB 字符串 + 其对象图

两侧峰值都从"50MB 级"降到"**2MB 级**"。

### 3.2 产物结构（native）

```
DOCUMENTS/question-bank-backup-<YYYY-MM-DD>/
  ├── manifest.json          # { format:'sharded_v1', date, stores:[{name, shards, count}], items:{...} }
  ├── questions-000.json     # 该 store 的一个分片：JSON 数组，≤2MB
  ├── questions-001.json
  ├── question_notes-000.json
  └── ...
```

- `manifest.json` 记录**每个 store 的分片数、每片记录数**，用于校验完整性
- 分片是**标准 JSON 数组**，可用 `JSON.parse` 直接读，不需要自定义解析器

### 3.3 写侧实现要点

- 新增 `appendFile`（已确认存在于 `@capacitor/filesystem`，`definitions.d.ts:514`，
  `AppendFileOptions` 同样支持 `encoding: 'utf8'`）用于**片内累积写**，或直接每片一次 `writeFile`
- **每片一次 `writeFile` 更简单**：片内已 ≤2MB，直接写整片即可，无需 appendFile
  → 写入次数 = 分片数（50MB / 2MB ≈ **25 次**），不是每记录一次
- 兼容性：**片内仍是合法 JSON 数组**，任何标准工具都能读

### 3.4 读侧实现要点

- `Filesystem.readdir()` 列出备份目录 → 读 `manifest.json` → 按 manifest 顺序逐片处理
- 每片处理完**显式释放引用**（置空数组 + 让 GC 回收），避免累积
- **旧版单文件备份必须仍能恢复**：恢复入口先探测文件头
  （有 `format: 'sharded_v1'` → 分片路径；否则 → 走现有单文件路径）

### 3.5 平台差异（**需王先生确认**）

| 平台 | 导出 | 恢复 | 说明 |
|---|---|---|---|
| native | 分片目录 | `readdir` 按目录恢复 | 本方案主要战场 |
| **Web** | **保持单文件 JSON 不变** | 保持选文件不变 | 浏览器内存充裕（GB 级），不需要分片 |

→ **Web 端行为完全不动**，只有 native 走分片。
→ 已知限制：**native 产出的分片备份无法在 Web 端恢复**（跨平台恢复需后续补）。

## 六、风险与回退

| # | 风险 | 对策 |
|---|---|---|
| R1 | 分片文件缺失/损坏 | manifest 校验分片数与记录数；不匹配**明确报错**，不得出现"恢复成功 0 题" |
| R2 | 恢复中途失败（部分 store 已写入） | 沿用现有覆盖式 `setItem` 语义（只增/覆盖，不删）；失败时提示"已恢复 X/Y 片"，可重试 |
| R3 | 目录权限/路径 | 沿用现有 `DOCUMENTS` 目录与 `getBackupPath()` 体系 |
| R4 | 写入耗时（~25 次桥调用） | 预期数秒到十几秒，**不再闪退**；真机实测确认（王先生验证） |
| R5 | 跨平台恢复受限 | 已知限制，记入待办；Web 端仅支持 Web 产出的单文件 |
| R6 | 旧备份文件无法恢复 | 恢复入口保留单文件兼容路径（3.4 节），**必须实测旧文件仍可恢复** |
| 回退 | — | 改动集中在 backup 模块，出问题可 `git revert` 单个 commit |
